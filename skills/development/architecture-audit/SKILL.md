# 架构体检

两个判据，按顺序问：**还要不要？** 不要的整个删掉。**该不该一起变？** 该一起变的放在一起，不该的不绑在一起，一切依赖比自己更稳定的东西。目标是代码更少、典型改动只落一处。

先只读查到第 3 步出报告，停下等用户选做哪几条。用户事先说了全做、不用等，就不停，标「待定」的修法跳过。

日志、脚本、探针与报告放工作目录 `$TMPDIR/arch-<项目>-<时间>/`（用户另指了就用用户的），不进仓库。

## 1. 圈范围

先读项目的 AGENTS.md、术语表与决策记录：已定的约定不重提，有证据推翻时写明冲突。用户指了模块、子系统或痛点就只看那里；否则在仓库根跑 `node <本技能目录>/cochange.mjs`（见 `--help`），提交与共同修改最多的文件是热点，先看它们。范围外的发现列在报告末尾；根因跨出范围时照写修法，标明范围要扩到哪。

范围含 3 个以上目录或包时，按 [fan-out](../../workflow/fan-out/SKILL.md) 按需选档，按目录拆片，每片交回问题及证据。

完成标准：范围写成一句话，每个片都已交回。

## 2. 列问题

逐处问两个判据，答错的记进工作目录的 `log.md`，一条一行，带文件:行。答错只有三类：

**不再需要**：删掉后没有人会发现。

- 死代码；没有调用方的导出、开关、配置项。
- 已被取代的旧路径：兼容层、回退分支、迁移完成后留下的双写。
- 透传包装。删除测试：想象删掉它，复杂度随之消失的是透传层；散回 N 个调用方的，它在干活。
- 永不变化的扩展点与配置；只有一个适配器的端口是假设，两个（通常生产 + 测试）才是真的。
- 过时或复述代码的文档与注释。

**隐藏联系**：必须一起变，代码却不显示。

- 逻辑或值的副本。
- 读另一个模块设置的全局、文件或环境。
- 一个功能按层拆散在多个目录。
- 调用方只能靠默契知道的调用顺序或约定。
- 隐式状态机：一个流程的状态散在标志、计数、回调与定时器里，没有一处列出状态与转换。先还原成状态与转换，再按事件先后与交错查：每个非终态都有出路（失败、取消、超时、重启后恢复）、同一状态两份来源、竞态。

**多余耦合**：绑在一起，却因不同原因而变。

- 调用方依赖内部实现。
- 稳定代码依赖更易变的代码。
- 通用函数带着只有一个流程懂的参数。
- 浅模块：接口几乎和实现一样复杂，内部一变接口跟着变。

另记每个**特殊情况**：针对单个值的 if、为某个调用方加的参数、吞掉的异常、重试或 sleep、被禁用的测试。它们多半是设计没考虑到的需求，用来反推系统真正要什么；外部协议、平台限制带来的标为保留。

每条问题标证据等级：**复现**、**代码**、**历史**、**推测**。共同修改只是线索，读过那几次提交、业务上确实要一起变才算隐藏联系。行为类怀疑（状态机、竞态、吞错、丢事件）写探针：复制项目的测试改写，放工作目录，带断言，断言过了才算复现。数字、报错原文、提交号从命令输出原样抄。查过排除的怀疑记一行理由（有意为之、测试替身依赖它、触发不了）。

在工作目录写一个提取脚本，产出报告数据；收尾对改后代码原样再跑。模块依赖用语言现成的工具取，静态取不到的（动态导入、反射、跨进程消息）写进范围说明。指标固定含一项范围内生产代码行数。数「几处」的指标按定义处数，收口后的调用不算；口径改了就回改前快照重跑，数不变才可用。

完成标准：范围内每个文件都扫过，每条问题有文件:行与证据等级，行为类怀疑都有探针结果，提取脚本已产出改前数据。

## 3. 按根因归并，出报告

假设系统从一开始就知道今天的需求，找一个修法解掉多条问题，它常常和症状长得不像；特殊情况不逐个修。日志改写成修法在上、问题缩进在下，修法写到能动手（新建或删掉哪个函数、类型、文件，调用方怎么改）：

```md
- 让通用 Dialog 关闭时把焦点还给打开前的元素，等待和全局标志都能删掉。
  - `ui/LogoutDialog.tsx:30` 关闭后等 100ms，指望输入框到时能拿到焦点。（代码）
  - `ui/SettingsDialog.tsx:61` 设全局 `skipRefocus`，阻止它打开的登出框抢焦点。（复现）
```

每条修法过同一道检验：改后该一起变的在一起，不该的不绑，依赖指向更稳定处。不落成万能管理器：展示、执行、存储各在其位，只收口确实要一致的规则；隐式状态机收成一处显式的状态与转换，其余地方只读它或只发事件。编号即执行顺序：先删除，再合并副本与收拢状态机，最后改结构；用到另一条修法改出的结构的排在它后面，其余按牵连问题数与热点程度。范围内有测试时，末位加一条「按 better-test 清理范围内的测试」：测试是重构期间的安全网，最后动。

重复定义直接收口。修法要引入新接口且几种做法各有代价的，或删掉会改变用户可见行为的（仍可触达的功能、仍有存量数据的旧格式），标「待定」，在修法里写清选项、代价与推荐。跨进程或跨部署的接口按 expand–contract 换。

范围内每个隐式状态机填进报告的 `machines`：改前是从代码还原出的状态与转换，有问题的状态或转换写明问题。

按「报告」生成报告，交给用户。用户要先看某条待定修法的方案时，按 [fan-out](../../workflow/fan-out/SKILL.md) 高档并行出 3 个以上截然不同的接口（最小接口、最大灵活、为最常见调用方优化；跨进程时加端口与适配器），每份写全类型、调用顺序、不变量与错误形态，比较后给推荐；要逐项对齐决策时用 [grilling](../../workflow/grilling/SKILL.md)。

完成标准：每条问题都归到一条修法，或标为保留并写明理由；报告已生成。

## 4. 逐条修

只做用户选定的修法。自建 worktree 与分支，主检出只读。动手前跑受影响的测试、类型检查、构建，记下原本就失败的项；范围内行为没有测试覆盖的，从真实入口（CLI、接口、页面）录下基线输出。

选定的修法改到状态机时，动手前写一个随机交错测试放工作目录：把对用户的承诺写成每轮结束都要成立的条件（总能走到终态、每次运行恰好一个结局、释放后不再被用、没有泄漏），在真实代码上随机排列操作，注入慢操作与失败，按种子可重放；再故意弄坏一处关键代码，确认它报得出来，否则它在空跑。

按编号顺序，每条修法：

1. 实现修法，删掉它让多余的特殊情况，留下系统仍需要的。
2. 跑受影响的验证，没有测试的走录基线的同一路径比对。第 2 步的探针改后再跑，原断言失败即问题消失；探针留在工作目录，不入库。改到状态机的修法，交错测试改后再跑，干净才提交：修法本身常引入新的交错缺陷，代码审查看不出。
3. 通过：一个提交。
4. 失败：行为真变了就修实现；测试绑死内部实现的按 [better-test](../better-test/SKILL.md) 判改写或删除，不降低断言求变绿。修了两次仍失败，丢弃本条未提交的改动，标「撤销」并写明卡点；后面要用到它的修法同样撤销。

旧测试不因模块合并就删：确认它守的行为已由新接口上的验证承接，再按 better-test 判。

完成标准：选定的每条修法都是已解、保留或撤销之一；原本就失败的项单独列出，没有算成通过。

## 5. 收尾

全量跑项目的测试与构建。按 fan-out 中档派只读子代理，按三类问题和特殊情况复扫改后的范围：有范围内的根因级问题就回第 3 步，只回一轮，再有的列为后续。改过状态机的，交错测试在改前、改后代码上各跑数百个种子：本次改动引入的问题回第 4 步修，不列为后续。重跑提取脚本，填入改后数据与改后的状态机，重生成报告。

不推送、不合并。交给用户：报告、分支、提交列表、每条修法的终态、没做的修法、原本就失败的项、后续与范围外的发现。

完成标准：复扫没有范围内的根因级问题，或已回过一轮、剩下的列为后续；改过状态机的，交错测试在改后代码上干净；前后数据出自同一个提取脚本。

## 报告

模板是 [report.html](report.html)，只读它顶部的字段注释。提取脚本把 JSON 写进模板副本的 `<script id="data">`，不改渲染代码；写完跑 `node <本技能目录>/check-report.mjs <报告>`，退出码 0 才算生成。
