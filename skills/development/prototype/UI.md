# UI 原型

在单一路由上生成**多个结构不同的 UI 变体**，用底部浮动栏切换。用户在浏览器里切换，选定一个或从几个里各取一部分，其余丢弃。

## 宿主：优先放进现有页面

变体贴着真实 header、sidebar、数据和密度时才好判断；空白路由里每个变体单独看都不错。

- **A：现有页面（默认）。** 变体在同一路由上渲染，由 `?variant=` 控制；现有数据获取、params、auth 全部保留，只切换渲染的子树。要原型化的东西还没有页面、但自然属于某个页面（dashboard 新区域、设置页新卡片、现有流程新步骤）时，也挂到那个宿主页面上。
- **B：新页面。** 只用于没有任何现有页面能承载的东西，比如全新的顶层界面。按项目已有路由约定建一次性路由（如 `/prototype/<name>`），路径或文件名带 `prototype`，同样用 `?variant=`。

## 流程

### 1. 定 N 并写计划

默认 3 个变体，上限 5 个；再多就分不出差异。在原型文件顶部注释写一行计划，例如：

> “设置页面的三个变体，通过 `?variant=` 切换，位于现有的 `/settings` 路由上。”

### 2. 生成结构不同的变体

每个变体都要符合页面目的及其能拿到的数据、项目的组件库与样式系统（TailwindCSS、shadcn、MUI、普通 CSS 等），并有清晰的导出名，如 `VariantA`、`VariantB`、`VariantC`。

变体之间在布局、信息层级、主操作方式上都不同。常见失败是同一个卡片网格换颜色、间距、圆角或文案出三份；要的是比如卡片网格、表格加侧边详情、分步向导这种结构差异。两个草案太像时，明确排除对方的结构（如“不用卡片网格”）重做一个。

变体可以共享 `<Header>` 这类小件，不共享 `<Layout>`：每个变体要能自由改布局。需要写操作时接 stub，不接真实 mutation。

### 3. 接上切换

```tsx
// 伪代码——按项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

### 4. 底部浮动切换器

屏幕底部居中的小型固定栏：

- **左 / 右箭头**：循环切换上一个 / 下一个变体。
- **变体标签**：当前 key，变体导出了名称就一起显示，如 `B — Sidebar layout`。

行为：

- 点击用框架 router 更新 URL search param（Next 用 `router.replace`，React Router 用 `navigate`），变体可分享、刷新后保持。
- `←` / `→` 键也能切换；`<input>`、`<textarea>`、`[contenteditable]` 聚焦时不拦截。
- 视觉上与页面区分（高对比胶囊、细阴影），一看就不属于被评估的设计。
- production 构建中隐藏（`process.env.NODE_ENV !== 'production'` 或等效检查），误合并也不会发给用户。

切换器做成独立组件，放在项目共享 UI 的位置。

### 5. 交付

给出 URL 和各 `?variant=` key。用户常见的反馈是“B 的 header 加 C 的 sidebar”，那就是他们要的设计。

### 6. 记录与清理

记下胜出的变体及理由，再按 [SKILL](SKILL.md) 第 6 条记录原型。胜者按生产标准重写进真实代码（原型代码没有测试、错误处理极少），完整变体集合留在一次性分支：

- **A**：胜者并入现有页面；主分支删除落选变体和切换器。
- **B**：胜者升为真实路由；主分支删除一次性路由和切换器。
